# T-003 — Endurecer HTTP (headers, límite de body, 400/413/404 en JSON)

## Objetivo
Que la API no anuncie Express, envíe tres headers de protección en toda respuesta, rechace cuerpos de más de 100 kb con `413`, JSON malformado con `400` y rutas inexistentes con `404`, siempre en JSON y sin stack.

- `ARQUITECTURA.md` → **C-003** (contrato exacto) y C-002 (cómo se testea)
- `CONVENCIONES.md` y `TROPIEZOS.md`
- Estándar: `kit/estandares/seguridad.md` (§3 HTTP)
- **Patrón de referencia a seguir:** `tests/health.test.js` (levantar `app` con `listen(0)`, `fetch` nativo, cerrar en `after`)

## Contrato a respetar
```
Toda respuesta:   sin X-Powered-By
                  X-Content-Type-Options: nosniff
                  X-Frame-Options: DENY
                  Referrer-Policy: no-referrer
Ruta inexistente → 404 {"error":"Recurso no encontrado"}
JSON malformado  → 400 {"error":"JSON malformado"}
Body > 100 kb    → 413 {"error":"Cuerpo demasiado grande"}   (JSON y urlencoded)
Content-Type: application/json; charset=utf-8 en los tres
```
Orden en `app.js`: `disable('x-powered-by')` → middleware de headers → parsers con `limit: '100kb'` → routers existentes (sin cambios) → 404 → manejador de errores de body. Detalle en C-003.

## Criterios de aceptación
| # | Criterio | Cómo se verifica | Falla cuando |
|---|---|---|---|
| 1 | Headers en respuestas 200, 400, 404 y 413 | `npm test` | algún caso no comprueba los tres headers y la ausencia de `x-powered-by`, o solo se prueba en la 200 |
| 2 | `404` exacto para ruta inexistente, en `GET /` y `GET /api/no-existe` | `npm test` | status ≠ 404, `content-type` no JSON o el cuerpo no es `deepStrictEqual` con el contrato |
| 3 | `400` exacto para JSON malformado | `npm test` | status ≠ 400 o cuerpo distinto del contrato |
| 4 | `413` exacto para JSON y para urlencoded de más de 100 kb | `npm test` | falta uno de los dos parsers o el cuerpo difiere del contrato |
| 5 | Un JSON válido de menos de 100 kb (ej. 90 kb) **no** recibe 413 | `npm test` | el test no existe o recibe 413 |
| 6 | Los demás errores no se tragan: el manejador llama `next(err)` si `err.type` no es de body | inspección del diff | responde 500 propio, o cambia el mensaje de otros errores (es E3) |
| 7 | Los routers existentes siguen montados igual y `tests/health.test.js` pasa | `npm test` + diff de `app.js` | se quita, reordena o altera un `app.use('/api', …)` existente |
| 8 | Sin dependencias nuevas y solo archivos permitidos | `git diff --stat origin/main...HEAD` | cambia `package*.json` o aparece otro archivo |

## Casos de abuso (obligatorio: seguridad sensible)
| # | Intento malicioso o no autorizado | Resultado esperado | Test |
|---|---|---|---|
| A1 | `POST /api/health` con JSON de ~150 kb | `413` con el cuerpo exacto; el cuerpo no contiene `PayloadTooLargeError`, `at `, `node_modules` ni `\\` | `tests/http-hardening.test.js` |
| A2 | El mismo tamaño como `application/x-www-form-urlencoded` (saltar el límite cambiando el tipo) | `413` igual que A1 | ídem |
| A3 | Cuerpo JSON comprimido con `Content-Encoding: gzip` que ocupa poco pero descomprime a más de 100 kb | `413` (el límite aplica después de descomprimir) | ídem, con `zlib.gzipSync` de `node:zlib` |
| A4 | JSON malformado `{mal` | `400` exacto; el cuerpo no contiene `SyntaxError`, `JSON.parse` ni `at ` | ídem |
| A5 | `GET /api/<script>alert(1)</script>` (reflejo de la ruta) | `404` exacto en JSON; el cuerpo no contiene `<script` ni la ruta pedida | ídem |
| A6 | Cualquier respuesta, incluidos A1–A5 | Sin `X-Powered-By`; con los tres headers | ídem |

## Notas del LIDER
- **Comprobado el 2026-09-24 en `main` @ `99531f4`** (Express 5.1.0): hoy la 404 y la 400 responden HTML con `X-Powered-By: Express`; 413 y 400 imprimen el stack. El límite por defecto de body-parser ya es 100 kb, pero **debe quedar explícito** en ambos parsers.
- Los errores de body-parser traen `err.type === 'entity.parse.failed'` (400) y `'entity.too.large'` (413). Úsalos, no compares `err.message`.
- El middleware de headers va **antes** de los parsers: si va después, las respuestas 400/413 salen sin headers (lo prueba A6).
- Un manejador de errores de Express tiene 4 parámetros `(err, req, res, next)`; con 3 no se registra como tal.
